# Архитектурное решение по логированию

## Откуда собираем логи

Логи нужны с бэкендов и инфраструктурных компонентов:

- Shop API, CRM API, MES API;
- Shop DB, MES db;
- RabbitMQ.

Фронтенды на этом этапе не покрываем — нам в первую очередь нужны серверные логи.

## Список логов уровня INFO

- создание заказа: время, `customer_id` или `api_client_id`, `order_id`, источник (B2C/B2B);
- изменение статуса заказа: время, `order_id`, `from_status`, `to_status`, сервис-инициатор;
- загрузка 3D-файла: время, `order_id`, `file_size`;
- старт и завершение расчёта стоимости в MES: время, `order_id`, длительность;
- публикация и приём сообщения RabbitMQ: время, `queue`, `event_type`, `order_id`;
- закрытие заказа: время, `order_id`.

## Другие уровни логирования

Используем все уровни из урока:

- **FATAL** — отказ инстанса, недоступность БД/RabbitMQ.
- **ERROR** — необработанные исключения, провалившиеся бизнес-операции, 5xx-ответы API.
- **WARN** — повторные попытки, обработка сообщения дольше ожидаемого, неверный пароль.
- **INFO** — штатные события из списка выше.
- **DEBUG** — в prod выключен, включается точечно при расследовании.
- **TRACE** — только в dev.

## Мотивация

Сейчас ошибки разбираются со слов клиентов. Логи дадут общий «дневник» событий и закроют разрыв между жалобой пользователя и фактом в коде.

Метрики, на которые влияет логирование:

- MTTR при разборе инцидентов;
- число эскалаций от поддержки к разработке;
- доля повторно открытых тикетов;
- количество жалоб B2B на «не пришёл заказ» (за счёт возможности найти и переотправить потерянные события).

## Где включать логирование и трейсинг в первую очередь

Команда не сможет покрыть всё сразу. Приоритеты:

1. **MES API + RabbitMQ.** Здесь сидят два главных источника жалоб: долгий расчёт цены и интеграция с CRM через очередь.
2. **CRM API.** Это «вход» B2B и точка, где заказ попадает в работу.
3. **Shop API.** Здесь начинается B2C-сценарий.

## Предлагаемое решение

Берём стек **ELK** (или OpenSearch, см. ниже) с агентом **Filebeat** на каждом инстансе.

- В каждое приложение подключаем штатный логгер фреймворка (Logback/Log4j2 для SpringBoot, Serilog для .NET). Формат — JSON с полями `@timestamp`, `service`, `level`, `message`, `order_id`, `trace_id`, `span_id`.
- На каждом хосте — Filebeat, читает логи и отправляет в Logstash.
- Logstash парсит, добавляет окружение, маршрутизирует в нужный индекс Elasticsearch.
- Kibana — UI для поиска и дашбордов.
- Под каждый источник — отдельный индекс с шаблоном (`shop-api-*`, `crm-api-*`, `mes-api-*`, `rabbitmq-*`).
- Маппинг **статический** — отключаем dynamic mapping, как рекомендует урок, чтобы не плодить лишние поля.
- Управление жизненным циклом — через **ILM**: ролловер по размеру, перевод старых индексов на «холодное» хранение, автоудаление по сроку.
- В каждой записи лога — `trace_id` и `span_id` из OpenTelemetry, чтобы из Kibana переходить в Jaeger.

### Политика безопасности

- Доступ к Kibana — через корпоративную SSO. Роли: `Поддержка` (только чтение), `Разработчик`, `DevOps`.
- Сеть Elasticsearch и Logstash — только приватная.
- В логи не пишутся пароли, токены, ключи API, платёжные данные, ПДн клиентов. Используем идентификаторы (UUID). Маскирование делается в логгере приложения и дублируется фильтром в Logstash.

### Политика хранения

- Отдельный индекс на источник.
- Логи приложений — 30 дней горячее, 60 холодное, затем удаление (урок советует не больше месяца для логов сервиса, держим запас).
- Размер шардов — 10–50 ГБ, как рекомендует урок. Ролловер по `max_primary_shard_size` и `max_age`.

### Что нужно для превращения сбора в анализ

- Алёрты в Kibana: всплеск `level: ERROR` / `FATAL`, появление сообщений в DLX, всплеск 5xx, специфические исключения (например, таймауты расчёта цены).
- Поиск аномалий: внезапный рост скорости создания заказов в N раз за минуту (возможный DDoS или дублирующая B2B-интеграция), резкое падение частоты определённого статуса (затык в одном из сервисов).

## Дополнительно — критерии выбора технологии

| Критерий | ELK | OpenSearch | Splunk |
|---|---|---|---|
| Лицензия | Elastic License | Apache 2.0 | Проприетарная |
| Стоимость | Бесплатное ядро, платные фичи | Полностью открытый | Платная подписка |
| Совместимость с нашим стеком | Beats/Logstash | Те же агенты | Свои universal forwarder |
| Алёртинг | В платной части / ElastAlert | Встроен | Встроен |
| ILM | Есть | Есть (ISM) | Свой механизм |

Берём **OpenSearch**: лицензия Apache 2.0, по функциональности почти идентичен ELK, бесплатный встроенный алёртинг. Splunk даёт лучшую аналитику, но на наших объёмах быстро становится дороже самой команды.
