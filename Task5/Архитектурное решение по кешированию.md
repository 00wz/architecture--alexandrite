# Архитектурное решение по кешированию

## Мотивация

Операторы жалуются на медленную загрузку дашборда MES со списком заказов. Пагинация и фильтры по статусам уже добавлены и проблему не сняли — данные тянутся напрямую из MES db при каждом запросе. Для оператора скорость отображения списка критична: кто первым взял заказ, тот и получит оплату.

Кешируем именно список заказов на дашборде MES. Он подходит под условия из урока: читается часто, меняется заметно реже, чем читается, допускает «отставание» на пару секунд без бизнес-ущерба. Расчёт цены, авторизацию и сами 3D-файлы не кешируем (это прямо запрещено в уроке: секреты — нет, бинарные данные — нет).

## Предлагаемое решение

Берём **серверное кеширование** в MES API. Клиентский HTTP-кеш здесь не подойдёт: страница динамическая, обновление статуса должно быть видно всем операторам, а не каждому по истечении своего max-age.

Движок — **Redis** (как в учебной практике курса).

Паттерн — **Cache-Aside**. Почему:

- сценарий read-heavy — на дашборд смотрят постоянно, а пишут (смена статуса) реже;
- модель в кеше отличается от модели в БД — храним готовый список под ключ, в БД лежат заказы построчно. Cache-Aside это позволяет, Read-Through требует совпадения моделей;
- при сбое Redis приложение продолжит работать, обращаясь напрямую к БД — устойчивость к сбоям кеша, как описано в уроке.

Почему не другие паттерны:

- **Read-Through** — при ошибке кеша запрос упадёт, у нас этого допустить нельзя.
- **Refresh-Ahead** — подходит для часто запрашиваемых и быстро меняющихся данных вроде спортивных трансляций, у нас не тот темп. Плюс ошибки кеша при Refresh-Ahead обнаруживаются не сразу.
- **Write-Through / Write-Behind** — паттерны записи, у нас преобладает чтение.

## Стратегия инвалидации

Программная инвалидация по ключу + TTL как страховка.

- В Redis храним список под ключом `mes:orders:list:status={status}:page={n}`.
- При смене статуса заказа MES API программно удаляет ключи затронутых статусов (тот, из которого заказ ушёл, и тот, в который пришёл).
- TTL 60 секунд — на случай, если программная инвалидация по какой-то причине не отработала (как и советует урок при Cache-Aside).

Почему не другие стратегии:

| Стратегия | Подходит? | Почему |
|---|---|---|
| Программная + по ключу (выбрана) | да | Инвалидация мгновенная, точечная, не сбрасывает лишнее |
| Только временная (TTL) | нет | Оператор будет видеть устаревший список до истечения TTL — а это противоречит мотивации |
| На основе запросов | нет | Триггер на стороне пользователя, мы не можем чистить кеш из браузера оператора |
| На основе изменений | по сути то же | Реализуется тем же кодом — приложение реагирует на событие смены статуса |
