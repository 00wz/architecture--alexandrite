# Архитектурное решение по трейсингу

## Где заказ может зависнуть

Заказ проходит через три приложения и очередь, и места, где он может потеряться или зависнуть:

- Shop API → Shop DB при сохранении состояния.
- CRM API → RabbitMQ и обратно.
- MES API ← RabbitMQ при чтении сообщений — здесь проще всего потерять обновление статуса.
- MES API при синхронном расчёте стоимости (2–30 минут).
- API user → MES API — внешний канал, через который B2B создают заказы.

Все эти сервисы и связи покрываем трейсингом.

## Данные, попадающие в трейс

- `trace_id` и `span_id` (база OpenTelemetry).
- `service.name`, окружение (dev/release/prod).
- HTTP: метод, путь, статус, длительность.
- RabbitMQ: имя очереди, тип события, результат публикации/потребления.
- Бизнес-контекст: `order_id`, `customer_id` или `api_client_id`, текущий статус заказа.
- Ошибки: тип исключения и сообщение без чувствительных данных.

## Мотивация

Логов в части мест нет, и любая жалоба «у меня заказ не пришёл» сейчас разбирается со слов клиента. Трейсинг позволит по `trace_id` собрать всю цепочку вызовов одного заказа и увидеть, в каком сервисе и на каком шаге он задержался.

Технические и бизнес-метрики, на которые влияет внедрение:

- p95 времени прохождения заказа от `INITIATED` до `MANUFACTURING_APPROVED`;
- доля заказов, у которых трасса прерывается на конкретном сервисе;
- MTTR при разборе инцидентов;
- количество жалоб B2C/B2B на потерянные или зависшие заказы.

## Предлагаемое решение

В качестве стандарта инструментации — **OpenTelemetry** (отраслевой стандарт, есть SDK под Java и C#). В качестве визуализатора — **Jaeger** (поддерживает OpenTelemetry, есть готовый all-in-one для dev).

Что внедряем:

- В Shop API, CRM API, MES API подключаем OTel SDK с автоматической инструментацией HTTP-фреймворков.
- Инструментируем работу с RabbitMQ — `trace_id`/`span_id` идут в headers сообщения, на приёмной стороне контекст восстанавливается (context propagation, как описано в уроке).
- Заводим отдельный спан вокруг расчёта цены в MES API.
- Поднимаем Jaeger Collector + Query/UI. Долговременное хранилище трасс — Elasticsearch.
- Прописываем `service.name` (`shop-api`, `crm-api`, `mes-api`) и окружение через `resource`.

Доработанная диаграмма: `Task3/jewerly_c4_model_tracing.drawio`.

## Компромиссы

- Третьесторонние клиенты публичного API не пробрасывают наш `trace_id` — трасса начнётся с границы нашего API. Это нормально, но это ограничение.
- При длительности расчёта цены до 30 минут спан будет «жить» долго. При необходимости разобьём его на дочерние шаги.
- На сложные интеграции через SDK без поддержки OTel поставить инструментацию сложно — там трейсинг работать не будет.

## Безопасность

- Доступ к Jaeger UI закрыт за корпоративной SSO. Зайти могут только сотрудники компании с актуальной учётной записью и ролями `Поддержка` / `Разработчик` / `DevOps`. Внешний доступ запрещён.
- Сетевой доступ к коллектору и хранилищу — только из приватной сети.
- В спаны не пишутся персональные данные клиентов и значения параметров SQL — только идентификаторы (UUID).
- Срок хранения трасс ограничен (например, 14 дней).

## Дополнительно — автоматический мониторинг прохождения заказа и алёртинг

На основе данных трейсинга строим отдельный поток метрик:

- длительность всей трассы заказа от первого спана до последнего;
- длительность пребывания заказа в каждом статусе.

Метрики экспортируем из OTel Collector в Prometheus, дашборд — в Grafana. Алёрты:

- p95 длительности `PRICE_CALCULATED` > 30 минут — команде MES;
- заказы, висящие в `SUBMITTED` дольше N часов — команде;
- заказы, у которых трасса прервалась (нет ожидаемого следующего спана) — самый «тихий» класс инцидентов.

На диаграмме это добавляет OTel Collector (между приложениями и Jaeger), стрелку OTel Collector → Prometheus и стрелку Prometheus → Alertmanager. Все новые элементы — зелёным цветом. Файл: `Task3/jewerly_c4_model_tracing_alerts.drawio`.
