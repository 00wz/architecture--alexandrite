# Выбор и настройка мониторинга в системе

## Мотивация

Сейчас о проблемах мы узнаём от клиентов и операторов. Яндекс Метрика после открытия публичного API уже не отражает картину — трафик B2B идёт мимо неё, а внутренние процессы (RabbitMQ, базы, MES API) ей не видны. Мониторинг даст возможность видеть деградацию раньше пользователя, ускорит разбор инцидентов и даст базу для решений «масштабироваться или подождать».

## Выбор подхода

Для HTTP-API (Shop API, CRM API, MES API) — **RED** (Rate, Errors, Duration). Это запросно-ориентированные сервисы, ровно тот случай, для которого RED создан.

Для инфраструктуры (инстансы приложений, БД, RabbitMQ) — **USE** (Utilization, Saturation, Errors).

Для будущего Redis (после задания 5) USE не используем — урок прямо говорит, что для систем с кешированием он работает плохо.

## Метрики

Из приведённого в задании списка беру:

- **RPS для Shop API, CRM API, MES API** — Rate в RED. Ярлыки: `endpoint`, `http_method`.
- **RPS per user для тех же API** — нужны после открытия публичного API, чтобы отличать аномального B2B-клиента от честной нагрузки. Ярлык: `api_client_id`.
- **Response time для тех же API** — Duration в RED. Главный показатель пользовательского опыта. Ярлыки: `endpoint`.
- **HTTP 500 для тех же API** — Errors в RED. Ярлык: `endpoint`.
- **HTTP 200 для тех же API** — нужны вместе с 500, чтобы считать долю успешных.
- **CPU % и Memory Utilisation для shop API, CRM API, MES API** — Utilization из USE. Ярлык: `instance`.
- **Memory Utilisation и Number of connections для shop db и MES db** — БД сейчас по одному инстансу, упрётся раньше всего.
- **Number of dead-letter-exchange letters in RabbitMQ** — каждое сообщение в DLX, как правило, означает потерянный или зависший заказ. Ярлык: `queue`.
- **Number of message in flight in RabbitMQ** — если очередь растёт быстрее, чем разбирается, MES или CRM не успевают обрабатывать. Ярлык: `queue`.

## План действий

1. Поднять Prometheus как time-series базу.
2. Поднять Grafana как UI к Prometheus.
3. Подключить клиентские библиотеки Prometheus в Shop API, CRM API, MES API (отдают метрики на `/metrics`).
4. Подключить готовые exporter’ы для PostgreSQL и RabbitMQ.
5. Настроить `scrape_configs` в Prometheus.
6. Собрать в Grafana два дашборда: «API сервисов» (RED) и «Инфраструктура» (USE).
7. Настроить алёрты: всплеск HTTP 5xx, рост сообщений в DLX, p95 latency выше порога, CPU/память выше порога, длина очереди выше порога.

## Дополнительно — показатели насыщенности

- **CPU API > 70% более 10 минут** → тикет, > 85% более 5 минут → алёрт дежурному. Порог из расчёта, что пиковая нагрузка обычно вдвое выше средней (из урока про Backpressure).
- **Memory PostgreSQL > 80%** → тикет, > 90% → алёрт.
- **Сообщения в DLX > 0 за 5 минут** → немедленный алёрт, любая запись в DLX — это потерянный заказ или статус.
- **Длина очереди RabbitMQ растёт более 5 минут подряд, потребление отстаёт от публикации** → алёрт, плюс это сигнал на включение Backpressure на стороне продюсера.
